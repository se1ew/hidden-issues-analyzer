# Последствия, приоритет и область API

18 октября 2026. Пакет из 15 пунктов: шесть последних задач фазы 10 и
первые девять фазы 11. Новых миграций в этом пакете нет.

## Что закрыто

1. Последствия публикуются только при точном вхождении в цитату. Категории:
   `reported_harm` — автор явно сообщает о вреде, `loss_of_use` — явно описана
   потеря возможности использования, `reported` — другие описанные последствия.
   При отсутствии доказательства — «не определены». Словарь консервативный,
   не заменяет проверку человеком; отрицания не получают категорию вреда.
2. Правило `support-masking-consequence-v1` сортирует по уникальной поддержке,
   затем числу отзывов с положительным контекстом, затем категории последствий.
   Формула: `support * 100000 + positiveContextCount * 10 + consequenceRank`,
   где rank 0/1/2/3. Максимум 2000 отзывов в запуске сохраняет порядок компонент.
   Версия, компоненты, объяснение и ограничение сохраняются в JSON снимка.
3. Распространённость и отрицательная тональность не исключают группу из списка.
   Обычный список включает все группы; фильтры применяются только явно.
4. При поддержке ниже minReviews показывается «Мало подтверждений».
5. Интерфейс называет порядок алгоритмическим приоритетом; критичность,
   вероятность и достоверность не объявляются измеренными. Обзор читает новые
   группы вместо старого hiddenScore.
6. Ручные примеры проверяют пропущенные оценки, один отзыв, повторные фразы,
   положительную/отрицательную тональность, нулевые знаменатели и неполное покрытие.
7. Контракты новых сущностей используют Zod, новые состояния и ограниченные ID.
8. Ошибки имеют `code`, `message`, необязательные `details`. Поле `error` оставлено
   как совместимый текстовый alias. Непредвиденная ошибка не раскрывает стек.
   Ошибки JSON, размера тела, файла и rate limit используют тот же формат.
9. Обзор, отзывы, аспекты, группы и графики принимают productId/runId/from/to.
10. Запуск требует выбранный товар на клиенте и productId на сервере;
    `POST /analysis/run` также использует строгую схему, глобального запуска нет.
11. Существующие список/детали/отмена/retry-failed и выбор публикации проверены;
    параметры ID дополнительно валидируются. Ошибка, отмена или отсутствие
    публикации не подменяются успешным результатом.
12. Доказательства, состояния и merge/split/link/restore используют существующие
    защищённые маршруты с проверкой владельца и вложенных ID.
13. Серверные фильтры групп: category, status (включая signal), minSupport,
    minMasking (доля положительного контекста 0..1), minPriority. Сортировки:
    priority/support/masking/aspect/state, direction asc/desc.
14. Фильтры и сортировка применяются ко всей публикации перед страницей;
    total — вся отфильтрованная выборка, ID — стабильное вторичное упорядочение.
    Публикация ограничена 2000 упоминаниями; JSON сортируется в памяти API.
    pageSize: группы/запуски до 100, доказательства/inputs до 50, отзывы до 200.
15. Ключи запросов включают владельца и применимую область/фильтры/страницу.
    Zustand хранит выбранный запуск и период отдельно от сохранённого товара;
    смена товара сбрасывает запуск и период. Выбранный в «Проблемах» запуск
    передаётся в обзор, отзывы и графики. После смены аккаунта кэш очищается,
    поздние ответы предыдущей сессии по-прежнему отвергаются API-клиентом.

## Область данных

`runId` требует `productId`. Период задаётся парой ISO timestamp с часовым
поясом, от from включительно до to исключительно. Для сохранённого запуска
период должен точно совпадать с его scope.period. Иначе 409 `scope_mismatch`
предлагает выбрать подходящий запуск или создать новый: срез готовой группы
изменил бы её поддержку и знаменатель. Без from/to читается вся область запуска.

`GET /analysis/stats?productId=P&runId=R` использует AnalysisRunReview и
ReviewAnalysis, включая исходные тексты/рейтинги до последующих изменений
отзыва. `issuesCount` относится к последней запечатанной публикации этого
запуска; при её отсутствии publicationId=null, issuesCount=0.
Отменённые/ошибочные запуски позволяют читать сохранённые результаты без
объявления их опубликованными.

`GET /analysis/aspects` требует товар и запуск, возвращает уникальные по
отзыву категории/названия/тональности. Один отзыв может иметь разные аспекты.
`GET /reviews` с runId использует тот же снимок, фильтрует всю область по
sentiment/rating/hasIssues/search и затем берёт страницу. Обычный список без
runId остаётся списком импортированных отзывов и поддерживает период reviewDate.
`GET /analysis/timeseries` с runId использует reviewDate и отдельно считает
unknownDateCount; отсутствующая дата не заменяется временем импорта.

## Совместимость и ограничения

Старые снимки неизменяемы: приоритет для них не выдумывается при чтении,
интерфейс предлагает пересчитать группировку. Новая публикация сохранит
историю и получит новую метрику; старые записи приоритетом не фильтруются.
Нельзя считать категории последствий подтверждением причины дефекта.
Свободные формулировки вне словаря получают общую категорию reported.

Без выбранного runId обзор и графики сохраняют переходную статистику:
перестройка всей аналитики, календарных сравнений и отчётов остаётся в
фазах 14–15. Общая панель выбора периода/покрытия и оформление — фаза 12.
Точечные invalidation, единое открытие запуска из всех кнопок и полная
приёмка контрактов с настоящим PostgreSQL/Redis/worker остаются следующими
пунктами фазы 11. Этот пакет проверяется управляемыми ответами БД и HTTP;
он не закрывает интеграционную приёмку настоящей очереди или локальной модели.

## Проверки

`npm run check`: 235 API + 40 web тестов, TypeScript, ESLint, SQL миграций в отдельной
PGlite и production-сборки. Новые тесты проверяют расчёты, отсутствие
неподтверждённых последствий, фильтры до страницы и total, права доступа,
scope_mismatch, частичные/отменённые/ошибочные результаты, формат ошибок,
запросы клиента и разделение кэша по владельцу.
