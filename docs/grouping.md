# Группировка доказательств запусков

18 октября 2026. Реализованы фаза 9 и первые пять задач фазы 10.

Worker после извлечения читает только успешные IssueMention из неизменяемого
снимка своего запуска. Параметры `grouping` и `embedding` сохраняются при
создании запуска; новый импорт не меняет его область. DBSCAN использует
нормализованные векторы и косинусную дистанцию. Внутри кластера дополнительно
ограничен попарный диаметр, чтобы цепочка соседей не объединяла далёкие точки.
Товары, запуски, scope и категории аспектов изолированы; неизвестные аспекты
дополнительно разделены по названию. Это консервативное правило, а не гарантия
семантического качества модели.

По умолчанию epsilon=0.25, minReviews=2, maxMentions=1000, representatives=4.
Ограничения схемы: epsilon 0.01..0.6, minReviews 2..20, maxMentions 1..2000,
representatives 1..8. Чрезмерный запуск получает понятную ошибку группировки
и не заменяет предыдущую публикацию. Одиночные и недостаточно поддержанные
группы сохраняются как сигналы, включая шум DBSCAN. Поддержка считается
по уникальным исходным отзывам, а не числу фраз.

Представитель — медоид; остальные цитаты выбираются из разных отзывов
с учётом разнообразия векторов. Заголовок составляется из исходного аспекта
и представительной жалобы: отдельный вызов LLM не нужен, недоступность
текстовой модели не мешает сформировать проверяемое название.

## Публикации и решения

GroupingPublication хранит новый набор IssueClusterSnapshot и все связи
IssueClusterMember. Последовательность: сохранить группы и связи, запечатать
публикацию, переключить Product.publishedGroupingId, завершить запуск в той
же транзакции. SQL запрещает изменение запечатанных групп/связей и публикацию
непригодного запуска; проверка терминального состояния отложена до COMMIT.
Ошибка, отмена, потеря lease или сбой сохранения не удаляют старый результат.
Пустая выборка запуска не заменяет ранее опубликованную область.

Стабильная Problem сопоставляется по точной нормализованной формулировке
дефекта, категории и scope среди всех её запечатанных исторических снимков.
Совпадение только общего слова, категории или заголовка недостаточно.
Однозначное взаимно уникальное совпадение сохраняет ID и пользовательский
статус. Неоднозначные кандидаты остаются на проверке; владелец может явно
связать группу с предложенной карточкой через предпросмотр. Семантическое
сопоставление перефразированных дефектов пока не гарантировано.

Состояния new/confirmed/rejected/resolved меняются с expectedVersion,
историей и причиной отклонения. Решённая карточка автоматически становится
new только при новом уникальном подтверждении, впервые импортированном
строго после решения. Повтор старых отзывов, даже в новом запуске, не
переоткрывает карточку; rejected сохраняется.

Объединение и разделение работают через предпросмотр и явное сохранение.
Каждое упоминание входит ровно в одну группу публикации; split должен
разделить весь состав без пропусков и дублей. Разные scope/категории нельзя
объединять. Изменённые группы получают новые карточки без копирования чужого
решения; неизменённые сохраняют ссылки. История содержит владельца, причину,
исходную и предыдущую публикации. Восстановление старой группировки внутри
того же запуска создаёт новую публикацию, не редактируя автоматический снимок.
Устаревший предпросмотр отклоняется с 409. История UI ограничена последними
100 публикациями; исходные записи в БД не удаляются.

## Независимые показатели

Старые severity/visibility/hiddenScore в новых снимках остаются null.
Последующий пакет добавил категории последствий и версионированный приоритет:
см. [priority-and-api.md](priority-and-api.md). Ниже описан исходный набор метрик.
В metrics сохраняются:

- support: уникальные отзывы группы C; mentionCount — отдельно;
- prevalence: C/N, где N — успешно обработанные отзывы именно этого запуска;
- coverage: total, succeeded, failed, remaining и succeeded/total;
- highRatingCount / knownRatingCount: доля 4–5 среди известных оценок группы;
- positiveSentimentCount / support: отдельная доля положительной тональности;
- positiveContextCount H: объединение рейтинга 4–5 и positive без двойного счёта.

Неизвестный рейтинг исключается из знаменателя оценок. Нулевой знаменатель
даёт null. Признак hidden требует product-scope и минимум minReviews
уникальных отзывов в положительном контексте. Общий негатив не становится
показателем серьёзности или статистической уверенностью. Пока используется
сортировка по поддержке; полноценное правило приоритета остаётся в фазе 10.

## Эмбеддинги и API

EMBEDDING_MODEL, EMBEDDING_REVISION и EMBEDDING_BATCH_SIZE фиксируются
в настройках запуска. Версия включает модель, revision, quantized/mean/L2
и transformers 2.17.2. Пакеты ограничены 16 текстами по умолчанию (1..64).
Процессный кэш ограничен 5000 векторами. Для 40-символьного commit SHA
используется также EmbeddingCache в БД. Mutable revision main кэшируется
только внутри процесса и не обещает воспроизводимость между перезапусками;
для постоянного развёртывания нужен проверенный commit. Worker держит не
более двух версий моделей одновременно. Отмена проверяется между пакетами
и после вычисления; уже начатый ONNX-вызов не прерывается посередине,
но его поздний результат не публикуется.

Все маршруты требуют владельца товара:

| Маршрут | Назначение |
| --- | --- |
| GET /api/issues/groupings?productId=...&runId=... | Текущая или выбранная группировка; page/pageSize до 100 |
| GET /api/issues/groupings?productId=...&publicationId=... | Историческая публикация |
| GET /api/issues/groupings/history?productId=... | Последние 100 публикаций |
| GET /api/issues/snapshots/:id/evidence | Все доказательства группы, пагинация до 50 |
| POST /api/issues/groupings/:id/edit | merge/split/link/restore, reason, expectedPublicationId, commit |
| PATCH /api/issues/problems/:id/state | status, expectedVersion, reason |
| POST /api/issues/recompute | Пересчёт выбранного runId в новую публикацию |

На странице проблем доступны выбор запуска/публикации, отдельные сигналы,
знаменатели, цитаты, история решений и исправления групп. Старые /issues
чтение/resolve сохранены для legacy-данных; destructive legacy-пересчёт
удалён. Обзор, аналитика и отчёты ещё используют переходные поля и будут
переведены в следующих фазах; их числа нельзя считать сводкой новых групп.

## Проверки и следующая точка

`npm run check`: 204 API + 35 web тестов, обе SQL-проверки в PGlite,
TypeScript, ESLint и production-сборки прошли. Размеченные примеры с
управляемыми векторами дали восемь ожидаемых групп товара и четыре скрытые
группы. Это проверка алгоритма на заданных данных, не оценка реальной модели.

`npm run benchmark:grouping`, Node 24.19.0, Windows, одинаковые синтетические
384-мерные векторы, только CPU-алгоритм:

| Упоминания | Время | Изменение heap | RSS процесса |
| --- | --- | --- | --- |
| 25 | 21 мс | 0.6 MiB | 75.7 MiB |
| 200 | 69 мс | 1.5 MiB | 81.7 MiB |
| 1000 | 1520 мс | 2.6 MiB | 117.5 MiB |

Это не пиковая память и не замер эмбеддингов, БД, GPU или полного задания.
Миграция `20261018150000_grouping_publications` проверена в отдельной БД
в памяти; к пользовательской БД ещё не применялась. Перед запуском нужны
`npm run db:generate` и `npm run db:deploy` на восстановленной инфраструктуре.
Docker/Redis/отдельный worker по-прежнему требуют интеграционной приёмки.

После этой проверки выполнен следующий пакет из 15 пунктов: фаза 10 закрыта,
первые девять пунктов фазы 11 закрыты. Подробности: [priority-and-api.md](priority-and-api.md).
Открытая проверка очереди фазы 7 сохраняется.
