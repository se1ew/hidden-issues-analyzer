# Приёмка качества локальной модели

Подготовка на основном ПК завершена. Качество настоящей instruct-модели ещё
не измерено. Этот протокол выполняется на целевом ПК до итоговой демонстрации.

До первого прогона запишите версию runtime, GPU/драйвер, модель и SHA-256 GGUF,
контекст, offload, parallel=1 и модельный ID. Установите неизменяемый
`LLM_MODEL_VERSION` в env. Согласуйте допустимые ошибки заранее. Ниже предложены
границы для пилота; они **не утверждены** и не являются измеренными результатами:

| Проверка | Предложение для согласования |
| --- | --- |
| Дословность всех опубликованных цитат и UTF-16-позиций | 100%; неверная цитата не публикуется |
| Валидные ответы после разрешённых повторов | Не менее 95% |
| Точность смысловых жалоб | Не менее 90% |
| Полнота смысловых жалоб | Не менее 80% |
| Отрицание/чужой опыт/предположение на контрольных примерах | Ни одной опубликованной выдуманной жалобы |
| Разные товары и разные дефекты одного аспекта | Не объединяются |

Эти проценты на малом наборе не доказывают качество на всех товарах. 25 отзывов
из репозитория — синтетический контроль для разработки. Нужен отдельный
проверенный человеком набор, не использованный при настройке промпта.

## Прогон

После сборки API настройте локального провайдера в окружении и выполните:

```powershell
node scripts/evaluate-model.mjs --output .cache/model-evaluation-01.json
# Другой набор того же формата:
node scripts/evaluate-model.mjs --dataset PATH_TO_CASES_JSON --output .cache/model-evaluation-holdout.json
```

В контейнерной установке команда выполняется внутри worker:
`node /app/scripts/evaluate-model.mjs --output /app/models_cache/model-evaluation-01.json`.
Запускайте её при простаивающем worker: это отдельный последовательный процесс.
Файл вывода должен быть новым; существующий не перезаписывается. Облачный
провайдер отвергается. Пользовательская БД не меняется, кэш ответов отключён.

Инструмент использует production-разбиение длинного текста, JSON-схему и
проверку доказательств. Он сохраняет вход, ожидаемую разметку, проверенный ответ,
пустой успех отдельно от ошибки, счётчики ответов/usage и время каждого отзыва.
API-ключ, внутренний URL и секреты не попадают в файл. Self-test:
`node scripts/evaluate-model.mjs --self-test`; он не оценивает настоящую модель.

## Проверка человеком и измерения

Для каждой строки заполните `adjudication`: TP — подтверждённые жалобы,
FP — лишние/выдуманные, FN — пропущенные. Сравнивайте смысл дефекта и scope,
а не буквальный текст `description`. Повтор одного дефекта в одном отзыве
считайте один раз. Проверяйте split/merge внутри товара по эталонным группам.
Точность = TP/(TP+FP), полнота = TP/(TP+FN); при нулевом знаменателе значение
не определено. Ошибочные ответы показывайте отдельной долей, не скрывайте их
исключением из отчёта. `precision`/`recall` намеренно остаются null до разметки.

Запишите проверяющего и согласованные пороги в `reviewedBy`/`approvedThresholds`.
Не меняйте границы после просмотра результата без нового отдельного опыта.
При непрохождении исправьте конфигурацию/модель и сохраните новый прогон.

Первый запрос, прогретые запросы и пачка сохраняются отдельно. Время запуска
самого runtime измеряйте отдельно: первый HTTP-запрос не равен холодной загрузке.
Пиковые VRAM/RAM наблюдайте периодически во время опыта (например, `nvidia-smi`
с интервалом 500 ms), а не только до/после. Повторите после отключения интернета.
Финальные цифры, ограничения и выбранный вариант перенесите в `local-model.md`
и `acceptance.md`; при демонстрации показывайте ограничения рядом с результатом.
