# Размеченные примеры

`review-cases.json` содержит 25 синтетических русскоязычных отзывов и восемь
ожидаемых групп дефектов товара. Это исходная авторская разметка для разработки;
проверена её внутренняя согласованность, но независимой экспертной проверки
и проверки ответов модели пока нет.

Покрыты похвала без жалоб, скрытая жалоба, обычный негатив, отрицание,
предположение, чужой опыт, доставка, продавец, внешняя и встроенная упаковка,
несколько жалоб, повтор внутри отзыва, отсутствие оценки, конфликт оценки
и тональности, разные дефекты одного аспекта и изоляция товаров.

Поля `sentiments` задают допустимые общие тональности, поскольку смешанные
отзывы допускают несколько трактовок. `positiveContext` остаётся однозначным:
в смешанных случаях с оценкой 4–5 контекст положителен независимо от тональности.
У r11 без оценки требуется `positive`; у r12/r25 положительная тональность
не ожидается. `ratingSentimentConflict` отмечает явное противоречие у r13.

`defect` — стабильная метка для сопоставления ожидаемых жалоб, а не буквальная
фраза, которую обязана выдать модель. `quote` — дословная минимальная цитата.
Допустима другая точная цитата, подтверждающая тот же дефект. Все цитаты одного
дефекта из одного отзыва дают одно подтверждение. Позиции будущего анализатора
проверять в исходной строке: UTF-16, начало включительно, конец исключительно,
`text.slice(start, end) === quote`.

Ожидаются четыре скрытые группы: заедающая крышка и шум чайника A,
потеря связи левого наушника, протекающий флакон. Жалобы из r06/r07
извлекаются, но не попадают в группы дефектов товара. r17 не объединяется
с товаром A. r10 не объединяется с заеданием крышки; r21 — с потерей связи.
Общий негатив r18 сохраняет тональность, но не даёт конкретного дефекта.

Порядок проверки будущего пайплайна:

1. Обработать каждый исходный текст production-анализатором и сохранить полный
   ответ, версию конфигурации, ошибки и длительность.
2. Сопоставить жалобы по смыслу, категории, области и дословной цитате;
   посчитать пропущенные и выдуманные жалобы отдельно.
3. Сгруппировать результаты внутри товара и сравнить состав каждой группы,
   положительные подтверждения и признак `hidden` с `expectedProductGroups`.
4. Проверить метрики с полным составом набора: kettle-a — 17 отзывов,
   kettle-b — 1, headphones-a — 4, bottle-a — 3. При ошибках анализа
   знаменатель уменьшать только на ошибки и показывать их отдельно.

Новые запуски используют структурированные complaints и сохраняют
IssueMention с проверяемой цитатой и UTF-16 координатами;
контракт описан в [extraction-evidence.md](../extraction-evidence.md).
Legacy-отзывы с `issues: string[]` не получают выдуманные цитаты задним числом.
Этот файл не загружается автоматически в пользовательскую БД.

Проверка структуры и согласованности разметки без модели, БД и зависимостей:

```powershell
node scripts/validate-review-cases.mjs
```

Валидатор проверяет только сам набор. Успешная проверка не означает,
что анализатор прошёл эти примеры. Для оценки качества нужен отдельный
реальный набор, не использованный при настройке промпта и кластеризации.

`extraction-provider.test.ts` пропускает заданные ответы для этих 25 примеров
через production HTTP-адаптер, схему и подготовку доказательств. Сарказм,
длинный текст и пустой ответ проверяются дополнительно. Модель в этих тестах
не генерирует ответы: семантическое качество настоящей LLM не оценивалось.
