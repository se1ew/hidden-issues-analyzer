# ReviewLens: принадлежность данных и текущие ограничения

12 октября 2026. Фаза 3: доступ через владельца товара, происхождение новых
импортов и cookie-сессии. Проверки будущих устойчивых запусков остаются открытыми.

Все маршруты товаров, отзывов, анализа, проблем, отчётов и парсинга требуют
access token. Списки, статистика, SQL-динамика, AI summary, фоновый анализ и
пересчёт legacy-кластеров ограничены `Product.userId`. Неизвестные и чужие
ID в операциях с одной записью дают 404; чужой товар в фильтре списка даёт
пустую выборку. Старые товары без владельца и непривязанные отзывы скрыты.
Владельцев назначают явно командой из `data-migration.md`.

CSV, ручной ввод и существующий парсер WB используют единый транзакционный
импорт. Товар принадлежит вызывающему пользователю; явный productId проверяется
в той же транзакции. Новые локальные товары используют source `local`,
отзывы — источник своего импорта. Для WB ключ товара — владелец, источник
`wildberries` и артикул. Отзыв с внешним ID уникален в пределах товара и
источника; первый текст, партия и importedAt при повторе не перезаписываются.
Каждая партия получает связи повторного появления. Без внешнего ID одинаковые
тексты сохраняются как разные отзывы. Конфликт одновременных импортов имеет
ограниченные транзакционные повторы.

CSV сохраняет исходный текст, читает external_id/review_id и author_id,
поддерживает сопоставление произвольных колонок и предпросмотр без записи в БД.
Ручной ввод тоже сохраняет пробелы исходного текста. Передача productId
позволяет дополнить существующий товар. Пользователь явно выбирает товар по ID
или создаёт новый; название больше не ищет существующие товары. После импорта
выбирается его товар для анализа. Строгая проверка UTF-8, рейтингов, дат и
размеров, статусы completed/partial и защищённый экспорт ошибок реализованы;
подробности — `csv-import.md`. Потоковый импорт и возобновление остаются в фазе 4.
Актуальность внешнего WB API и восстановление парсинга относятся к фазе 5.

Socket.IO требует JWT в handshake.auth.token. Подписка и replay разрешены
только владельцу задания; случайный UUID не заменяет эту проверку. Соединение
закрывается при истечении access token. Отмена чужого задания даёт 404.
Запуск требует конкретного товара владельца; создание, чтение истории,
отмена и socket-replay проверяют сохранённый AnalysisRun и владельца товара.
Удаление товара блокируется при активном запуске в PostgreSQL; проверка и
создание координируются блокировкой строки товара. Исторические AnalysisRun
также пока препятствуют удалению: очистка истории и артефактов не реализована.
Устойчивая очередь описана в [analysis-worker.md](analysis-worker.md).

Новые legacy-отчёты генерируются только по данным владельца и сохраняют
проверенную ownerScope. Старые отчёты без подтверждённой области скрыты:
прежний генератор мог включить чужие отзывы даже в отчёт с userId автора.
Новые отчёты со связью с товаром доступны владельцу этого товара и записи.
Публичные ответы не включают filePath. Скачивание требует авторизации;
русские имена файлов передаются через Express download. Переход на снимок
конкретного запуска и полный экспорт — фаза 15.

CORS разрешает только WEB_ORIGIN; без Origin доступны обычные API-клиенты
с токеном. На выходе и при смене пользователя клиент отменяет запросы,
очищает QueryClient, сбрасывает выбранный товар и отключает сокет.
Access token и пользователь хранятся только в памяти; прежняя запись hia-auth
удаляется из localStorage. После перезагрузки клиент восстанавливает сессию
через refresh до открытия страниц. Refresh token передаётся только в HttpOnly
cookie hia-refresh с Path=/api/auth, SameSite=Lax и сроком JWT_REFRESH_TTL;
при WEB_ORIGIN с HTTPS включён Secure. API и frontend должны быть same-site;
локальный HTTP поддерживается на localhost. HTTPS frontend требует HTTPS API.

POST register/login/refresh/logout требуют X-ReviewLens-CSRF: 1 и разрешённый
Origin, если он присутствует; Sec-Fetch-Site: cross-site отклоняется. Заголовок
в браузере требует разрешённого CORS preflight; клиенты без Origin также
обязаны его передавать. Refresh token из JSON больше не принимается и
не возвращается. Ответы сессии имеют Cache-Control: no-store.

Каждый refresh JWT имеет случайный jti; атомарное погашение в транзакции
не позволяет двум запросам одновременно ротировать один токен. Срок БД и
cookie берётся из exp JWT, а не фиксированных семи дней. Logout отзывает
текущий токен и цепочку его преемников, включая гонку с refresh другой вкладки,
и удаляет cookie; другие входы пользователя сохраняются. Выданный access JWT
остаётся действительным до exp — общего списка отозванных access-токенов нет.
При ошибке серверного logout клиент сохраняет сессию и предлагает повторить выход.

В одной вкладке параллельные 401 используют общий refresh. Ответы запросов
прошлого аккаунта отклоняются; запоздалый refresh не восстанавливает его сессию.
Между вкладками refresh не синхронизирован: конкурентный проигравший запрос
получает 401, не удаляя cookie, установленную победившим. Вход/регистрация
ограничены общим лимитом 20 попыток с одного IP за 15 минут, пароль — максимум
72 байта UTF-8 во избежание усечения bcrypt. Для отсутствующего email и
неверного пароля сообщение одинаковое. Настройка trust proxy остаётся текущей:
один доверенный reverse proxy; production API необходимо закрыть от прямого
доступа извне, чтобы клиент не мог подменять IP через X-Forwarded-For.

## Проверка

```powershell
npm run build:api
node scripts/verify-access-boundaries.mjs
```

Команда создаёт отдельный временный PostgreSQL, применяет миграции и проверяет
на настоящем Express/API и Socket.IO cookie-вход/регистрацию, ротацию,
конкурентный refresh, повтор старого токена, отзыв сессии, гонку logout/refresh,
независимые входы, два аккаунта, анонимный доступ, чужие ID,
выборки и изменения, статистику, скачивание DOCX с русским именем, скрытие
непроверенных старых отчётов, импорт с внешним ID, исходный текст,
сохранение первого происхождения, откат ошибочной транзакции и конкурентный
импорт. Не обращается к облачной LLM или настоящему WB API. Сгенерированный
тестовый отчёт и собственный временный контейнер удаляются после проверки.
Ожидаемые ошибки Prisma при проверке отката/конкуренции могут появиться в логе.

Все эти проверки прошли; также прошли 119 API + 22 web тестов, TypeScript,
ESLint и обе production-сборки. Фаза 3 повторно проверена и закрыта 20 октября: доступ к новым запускам,
доказательствам, отчётам и онлайн-импорту включён в интеграционные сценарии.
