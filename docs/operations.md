# Диагностика и обслуживание

Актуально на 20 октября 2026. Перед запуском выполнить `npm run db:generate`,
`npm run db:deploy`, `npm run build`. Сохранённые миграции включают очередь
отчётов, heartbeat, кэш извлечения, контрольные точки импорта и удаление товара.
Новые миграции проверены на временных БД; пользовательская БД в аудите не менялась.

## Доступность

- `GET /health`: процесс API жив; не обещает доступность зависимостей.
- `GET /ready`: PostgreSQL, Redis и живой worker; 200 либо 503. Проверки ограничены
  по времени, модель не входит в готовность чтения сохранённых данных.
- `GET /api/diagnostics`: те же сведения после авторизации; отображаются в профиле.
- `POST /api/analysis/provider/check`: отдельная явная проверка настроенной модели.

Worker обновляет heartbeat каждые три секунды, срок — 15 секунд. API и worker
сохраняют requestId/runId/importId/reportId в контексте структурированных логов.
HTTP-логи содержат метод, статус и ID запроса, не текст отзыва или токен.
Известные ошибки различают память модели, недоступность очереди и неверный формат
источника. Остановка модели не закрывает доступ к сохранённым отчётам и цитатам.

Анализ и онлайн-импорт используют BullMQ с состоянием в PostgreSQL. Диспетчер
повторно ставит ожидающие задания после потери Redis. Для онлайн-источника действует
общий лимит один импорт на все worker и до трёх запросов карточек одновременно;
отмена и таймаут прерывают запросы. Прерванный онлайн-импорт можно запустить снова:
внешние ID защищают уже сохранённые отзывы. CSV возобновляется повторной отправкой
того же файла с теми же параметрами.

Отчёты имеют queued/running/completed/failed/expired, сохраняют снимок до рендера
и формируются в дочернем процессе. Чтение статуса и скачивание не вызывают анализ.
После истечения lease задание возвращается в очередь; после трёх попыток нужна
явная повторная генерация. Истёкший файл восстанавливается по прежнему снимку.

## Ограничения и завершение

JSON-запрос — до 1 МиБ; CSV — 25 МиБ, 10 000 записей и 10 000 символов отзыва;
пакет — 100 записей. Экспорт — до 2000 строк/20 МиБ; источник — до 2000 отзывов/
4 МиБ. Ответ модели — до 2 МиБ, список моделей — до 8 МиБ. Превышение отклоняется
явно, частичная выдача не подписывается как полный результат.

Production worker запускается с heap 768 МиБ; дочерний renderer — 384 МиБ,
таймаут рендера — 120 секунд, lease — 150 секунд. API/worker получают 15 секунд
на штатное завершение; уже записанные результаты сохраняются. Эти программные
лимиты не заменяют замеры VRAM и модели на целевом ПК.

## Очистка

```powershell
npm run storage:inspect
# После просмотра списка применить ту же политику:
npm run storage:inspect -- --apply
```

Без `--apply` команда не удаляет данные. Политика: исходные ответы модели — семь
дней, диагностические подробности — 90 дней, файлы отчётов — 30 дней, бесхозные
артефакты/временные CSV — сутки, кэш извлечения — семь дней. Завершённые задания
BullMQ удаляются; ошибки доставки ограничены 100 заданиями. Статусы/коды ошибок,
снимки входов, цитаты, членство групп и решения пользователя сохраняются.
Из диагностики удаляются только временные `providerError`/`rawError`/`trace`;
признак отсутствующих доказательств, legacy-жалобы, единицы позиций и метрики
исполнения сохраняются, поскольку влияют на трактовку исторического результата.

Файлы удаляются только по допустимому имени непосредственно внутри каталога
отчётов или временных загрузок. Подкаталоги, переходы наверх и символические
ссылки не обходятся. Очистка и backup используют общий advisory lock.

## Резервное копирование и восстановление

Команды работают с локальным Docker PostgreSQL; имена контейнера и каталогов
передаются явно, абсолютные пути одного компьютера не встроены в скрипт.

```powershell
npm run storage:backup -- --container hia-postgres --directory .cache/backups/demo-2026-10-20
# Создать отдельную ПУСТУЮ БД и указать её DATABASE_URL в окружении:
npm run storage:restore -- --container hia-postgres --directory .cache/backups/demo-2026-10-20 --reports .cache/restored-reports
```

Backup содержит согласованный `pg_dump` и файлы готовых отчётов с SHA-256.
Restore проверяет контрольные суммы, пустую целевую БД и пустой каталог. Рабочая
БД с существующими таблицами не перезаписывается. После восстановления пути
артефактов обновляются, старые heartbeat удаляются, активные lease инвалидируются.
Проверено восстановление в отдельную БД: количества отзывов/доказательств,
снимок отчёта и байты файла совпадают; повтор в непустую БД отклонён.

Для другой ОС/сервера и больших БД нужен отдельный проверенный способ backup;
текущая команда ограничивает размер dump 256 МиБ. Перед рабочим восстановлением
API/worker целевой установки должны быть остановлены.
