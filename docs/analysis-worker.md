# Устойчивые запуски анализа

Обновление 18 октября: интеграционная проверка фазы 7 теперь пройдена на
временных PostgreSQL/Redis, включая crash/restart и разрыв TCP Redis.
Ниже сохранены этапы реализации; актуальный результат и команды:
[interface-and-run-sync.md](interface-and-run-sync.md).

12 октября 2026. Реализованы первые десять задач фазы 7.

API принимает `POST /api/analysis/runs` с обязательным `productId`, проверяет
владельца и доступность модели, затем в одной транзакции сохраняет запуск,
неизменяемые входные отзывы и pending-результаты. Снимок включает исходный
текст, рейтинг, дату, версию и hash входа, область выборки, настройки модели
и текст промпта. API-ключ в снимок не попадает. Блокировка товара и существующий
частичный уникальный индекс исключают два активных запуска одного товара.
Новая миграция для этих ограничений не требуется.

BullMQ доставляет runId отдельному worker. PostgreSQL остаётся источником
состояния: диспетчер периодически добавляет сохранённые queued-запуски,
если доставка в Redis не состоялась. Worker получает исключительный lease,
обновляет heartbeat и сохраняет попытки, этап, результаты и счётчики.
Токен и срок lease проверяются в транзакции записи; повторная доставка и
повтор результата не создают аспекты повторно. Истёкший running становится
interrupted, либо cancelled при ранее принятой отмене. Автоматическое
продолжение прерванных входов и повтор только ошибок ещё не реализованы.

`processed = succeeded + failed`, `remaining = total - processed`.
Все ошибки дают failed, часть ошибок — partial. Успешное извлечение жалоб
пока даёт partial с `grouping_pending`: проверяемая группировка ещё отсутствует.
Успешное извлечение без жалоб завершает запуск с пустыми группами; пустая
выборка завершается с причиной `empty_selection`.

Отмена сохраняется в БД. Worker проверяет её heartbeat-циклом и между входами,
прерывает HTTP-запрос и не записывает поздний ответ. Сохранённые результаты
остаются в запуске; cancelled/interrupted не заменяют предыдущую публикацию.
Переходная публикация результатов completed/partial записывает legacy-поля
отзыва только при совпадении текста и версии источника. Это ещё не система
версионированных доказательств и публикаций из последующих фаз.

`GET /api/analysis/runs?productId=...` и `GET /api/analysis/runs/:runId`
возвращают состояние из БД только владельцу. `POST /api/analysis/runs/:runId/cancel`
идемпотентен. Старые `/run` и идентификатор jobId сохранены как совместимые
алиасы; новый jobId равен runId. Socket.IO через Redis сообщает об изменениях,
затем читает актуальную БД. UI восстанавливает историю и активный запуск
через HTTP; polling работает и при потере socket. Старое правило трёх секунд
и сохранение прогресса в sessionStorage удалены.

## Запуск

```powershell
npm run dev                  # API, web и worker
npm run dev:worker           # только worker
npm run build
npm run start:api
npm run start:worker         # отдельный терминал
```

Оба серверных процесса используют конфигурацию `apps/api/.env`.

| Настройка | По умолчанию |
| --- | --- |
| ANALYSIS_QUEUE_NAME | analysis-runs-v1 |
| ANALYSIS_WORKER_CONCURRENCY | 1 |
| ANALYSIS_HEARTBEAT_MS | 1000 |
| ANALYSIS_LEASE_MS | 30000, не меньше трёх heartbeat |
| ANALYSIS_DISPATCH_MS | 2000 |

Глобальная конкуренция BullMQ ограничена минимумом worker concurrency и
LLM_CONCURRENCY. Все API и worker дополнительно используют общий Redis-семафор
`<ANALYSIS_QUEUE_NAME>:llm-capacity` с лимитом LLM_CONCURRENCY (по умолчанию 1).
Он охватывает сводки, preflight и извлечение; настройки разных процессов
должны совпадать. Диспетчер восстанавливает и глобальный лимит BullMQ
после потери Redis. Измерения нагрузки GPU остаются в фазе 18.

## Проверка

```powershell
npm run check
node scripts/verify-analysis-runs.mjs
node scripts/verify-access-boundaries.mjs
```

119 API + 22 web теста, TypeScript, ESLint и обе сборки прошли.
Интеграционные проверки используют управляемую HTTP-модель и временную БД.
Проверка очереди поднимает собственный Redis и отдельный настоящий worker:
двойной старт, неизменяемый снимок, идемпотентность, отдельные счётчики,
терминальные состояния, отмена активного HTTP, потеря lease, SIGKILL и
восстановление доставки queued после запуска нового worker.
Проверка доступа использует уникальное имя очереди и проверяет HTTP/socket
изоляцию владельцев, replay и анализ отдельным fixture-worker.
Пользовательские данные не очищаются, облачная генерация не вызывается.

Результаты проверки выше относятся к версии от 12 октября.

## Изменения 18 октября 2026

`POST /api/analysis/runs/:runId/retry-failed` создаёт новый запуск только из
failed-входов завершённого запуска. Снимок текста, hash, версии, даты,
рейтинга, конфигурации и промпта копируется из исходного запуска, а не
из изменяемого отзыва. `previousRunId` и `scope.retry` сохраняют происхождение.
Одновременные повторные нажатия блокируются общей блокировкой товара.
Успешные входы и исходный запуск не меняются; повтор без ошибок даёт 409,
чужой ID — 404. Отменённые и прерванные запуски возвращают
`resultsDisposition=retained_unpublished`; интерфейс объясняет, что сохранённое
не заменяет последнюю публикацию, и показывает кнопку повтора ошибок.
Повтор не объединяет результаты запусков в новый общий опубликованный снимок.

Диспетчер сверяет все queued-запуски постранично, восстанавливает доставку
и глобальный лимит очереди после потери Redis. Истёкший lease по-прежнему
переводится в interrupted (или cancelled), без автоматического повторения
HTTP-запроса с неизвестным исходом. Успешно сохранённая часть остаётся в БД.
Автоматическое продолжение pending-входов прерванного запуска не добавлено.

Redis-семафор выдаёт разрешение на обращение к модели с TTL 10 секунд и
продлевает его каждую секунду. Потеря разрешения отменяет HTTP-запрос;
при недоступном Redis обращения к модели не запускаются. После аварийного
завершения процесса разрешение истекает. Фактическое прекращение вычислений
на стороне runtime после закрытия HTTP зависит от самого runtime; проверка
нагрузки и поведения GPU отложена до фазы 18.

При остановке worker прекращается выдача новых входов, отменяется активный
HTTP, сохраняется interrupted и ожидается завершение текущей сверки очереди
до отключения БД. API ждёт завершения HTTP (до 5 секунд), отключает socket
и ждёт диспетчер. Отключение клиента отменяет запрос сводки.

Новые запуски используют `review-evidence-v2` / `extraction-v2`:
общая тональность, все аспекты и структурированные жалобы с aspectIndex,
scope, description, quote, assertion и nullable consequences.
Только assertion=experienced становится IssueMention. Остальные случаи
(отрицание, условие, отсутствие опыта) не публикуются как дефект.
Цитата должна находиться в исходном тексте; последствия допускаются только
как фрагмент цитаты. Сохраняются AspectMention и IssueMention в транзакции
результата. Legacy-v1 запуски обрабатываются старым контрактом.
Качество классификации самой LLM пока не измерено; программные проверки
не доказывают качество настоящей модели. Нормализация, неоднозначные цитаты,
публичный контракт offsets, группировка и окончательный экспорт ещё открыты.

`npm run check` прошёл: 133 API + 24 web теста, TypeScript, ESLint и обе
production-сборки. Новые тесты проверяют схему и границы доказательств,
классификации утверждений, остановку worker, поздний ответ, повторную доставку,
ожидание общего лимита и UI повтора/отмены.
`scripts/verify-analysis-runs.mjs` дополнен сценариями повторов только ошибок,
конкурентных повторов, сохранения неопубликованной части, потери Redis
и общего лимита API/worker. Fixture-модели обновлены под v2.
Эти новые интеграционные сценарии **не прошли приёмку в этой сессии**:
Docker Desktop не запустился из-за ошибки сокета Secrets Engine, скрипт
остановился при создании временной БД. После восстановления Docker повторить
`node scripts/verify-analysis-runs.mjs` и `node scripts/verify-access-boundaries.mjs`.
