# Модель данных и добавочная миграция

## Завершение перехода — 20 октября 2026

`20261020152000_archive_legacy_review_results` сохраняет прежние результаты
отзывов в `LegacyReviewResult.payload`, затем удаляет из `Review` поля
`hiddenIssueId`, `cleanedText`, `legacyAnalysis`, `sentiment`, `sentimentScore`,
`aspects`, `issues`, `analyzedAt`. Исторические `HiddenIssue` остаются архивом;
их прежние связи читаются из payload и не считаются доказательствами.

Текущие результаты вычисляет SQL view `CurrentReviewAnalysis` из неизменяемых
входов и успешных результатов завершённых/частичных запусков. Текст, версия,
рейтинг и дата должны совпадать с источником; отменённые и прерванные запуски,
ошибки группировки и неопубликованные жалобы не заменяют прошлый результат.
Редактирование входа возвращает отзыв в ожидающие обработки. Live-фильтры,
полный CSV, счётчики и режим «только новые» используют это представление.
Сводка AI читает опубликованный запуск, как аналитика и отчёт.

Проверены архив прежних значений, отсутствие удалённых колонок, миграция копии
7 реальных отзывов, SQL, 284 API-теста, доступ двух пользователей, настоящая
очередь/worker, отмена повторного анализа, live-фильтры, CSV и отчёты.
View поддерживается миграцией SQL; не заменяйте его таблицей через `db push`.
Восстановление старой схемы — из проверенной резервной копии.

## Обязательный владелец — 20 октября 2026

Миграция `20261020150000_require_product_owner` делает `Product.userId`
обязательным. При наличии товара без владельца она отказывается от изменений
с инструкцией явно назначить владельца; данные не распределяются автоматически.
Команда назначения работает с переходной схемой и актуальным Prisma Client.
Проверяются отказ на неназначенных данных, назначение, запрет переназначения,
NOT NULL, чистая установка и миграция копии пользовательской базы.

Перед проверкой в текущей БД: 3 пользователя, 3 товара, 7 отзывов, 0 товаров
без владельца и 0 отзывов без товара/партии. Ниже сохранено описание предыдущих
этапов; nullable-владелец относится только к состоянию до новой миграции.

## Обязательное происхождение отзыва

Миграция `20261020151000_require_review_provenance` требует товар и первый
импорт для каждого отзыва. Составной внешний ключ запрещает ссылку на партию
другого товара. При неустановленном происхождении миграция останавливается.
Для старой схемы оператор может явно подтвердить известное соответствие:

```powershell
node scripts/link-legacy-review.mjs --review REVIEW_ID --product PRODUCT_ID --batch BATCH_ID --reason "Основание проверенного соответствия"
# Добавьте --apply после просмотра. Не создавайте вымышленное происхождение.
```

Команда не меняет существующие связи, проверяет владельца партии, сохраняет
основание назначения в диагностике и выполняется транзакционно. Текст, даты,
рейтинг и внешний ID остаются прежними. Проверены предварительный просмотр,
отказ при пропущенных связях, явное связывание синтетической старой базы,
запрет чужой партии и миграция копии всех 7 пользовательских отзывов.

12 октября 2026. Фаза 2 реализуется без удаления старых таблиц и полей.
Миграция `20261012120000_add_analysis_domain` выполняется одной транзакцией.
Сначала проверена отдельная копия БД. Затем сохранена и восстановлена на
отдельном PostgreSQL резервная копия локальной БД; миграция применена к
локальной `hia_db`. Старые данные не получили автоматически назначенных владельцев.

## Что добавлено

`Product` получает владельца, источник и внешний ID. Уникальность внешнего
товара задаётся `(userId, source, externalId)`, внешнего отзыва —
`(productId, source, externalId)`. Название и текст не являются ключами
дедупликации; отсутствующие внешние ID допускаются.

`Review.uploadBatchId` хранит первый импорт, `importedAt` — время первого
появления. `ReviewImportOccurrence` хранит повторные появления без изменения
первичного происхождения. `UploadBatch` получает товар, статус, счётчики и
диагностику. Поле `text` остаётся исходным текстом, `cleanedText` — отдельным.

`AnalysisRun` хранит область, конфигурацию, версии метода, счётчики, lease и
времена. `AnalysisRunReview` хранит фиксированный состав и входные снимки;
изменение снимка запрещено SQL-триггером. При удалении исходного отзыва
ссылка очищается, а текст, исходный ID и доказательства остаются. В снимок
нельзя включить отзыв другого товара или другой версии входных данных.
Отпечаток входа вычисляет будущий сервис создания запуска.

`ReviewAnalysis`, `AspectMention` и `IssueMention` отделяют результаты от
исходного отзыва. Несколько жалоб одного отзыва сохраняются независимо.
Цитата хранится вместе с диапазоном `[quoteStart, quoteEnd)` в исходном
снимке; позиции задаются в кодовых единицах UTF-16, как `String.slice` в JS.
Диапазон проверяется БД на неотрицательность; дословность, верхнюю границу
и смысл цитаты должен проверить сервис извлечения фазы 8.

`IssueClusterSnapshot` и `IssueClusterMember` фиксируют группы конкретного
запуска. `Problem` и `ProblemEvent` сохраняют карточку и историю решений;
`stateVersion` и уникальное событие версии подготовлены для защиты от гонок.
`AnalysisRunEvent` хранит историю статусов запуска. Реализация разрешённых
переходов, lease и атомарных счётчиков относится к фазам 7–10.

Составные внешние ключи защищают принадлежность запуска владельцу товара,
результата входу запуска, жалобы аспекту своего анализа и кластера своему
запуску/товару. Частичный уникальный индекс разрешает один активный запуск
на товар. CHECK-ограничения проверяют счётчики и полноту `completed`.
Индекс, CHECK-ограничения и триггеры поддерживаются в SQL: Prisma schema
не описывает их, поэтому будущие миграции требуют проверки этого SQL.

`Report` получает товар, запуск, параметры и метаданные артефакта. Старое
`filePath` сохранено для совместимости. Перевод генератора на новые поля и
исключение пути из публичных ответов ещё предстоят в фазах 3 и 15.

## Старые данные и переходный период

Владелец товара временно nullable; отзывы и старые импорты могут оставаться
без связи. Это переходная схема, а не завершённый обязательный контракт.
Назначать владельца всем старым данным автоматически нельзя. Новые запуски
требуют реального владельца и соответствующего ему товара.

Для явного назначения конкретного товара существующему пользователю:

```powershell
# Предварительный просмотр, без записи
node scripts/assign-legacy-product.mjs --product PRODUCT_ID --user USER_ID
# Применение проверенного соответствия
node scripts/assign-legacy-product.mjs --product PRODUCT_ID --user USER_ID --apply
```

Команда использует `apps/api/.env`, не меняет существующего чужого владельца
и выполняет назначение транзакционно. Отзывы наследуют принадлежность от
товара. Исторические партии и отчёты не связываются по догадкам. Отзывы без
товара требуют отдельно проверенного назначения; автоматического слияния нет.

Для старых отзывов `importedAt` берётся из `createdAt`; анализированные записи
помечаются `legacyAnalysis`. Старые `HiddenIssue` и отчёты имеют `legacy=true`.
Цитаты, карточки новых проблем и успешные новые запуски не создаются из
старых агрегатов. Текущий анализатор также помечает новые результаты старого
пайплайна `legacyAnalysis=true`, пока не подключены запуски с доказательствами.
Исторические партии получают `legacy` и пометку о том,
что счётчики и происхождение не проверены.

Текущие сервисы ещё читают старые поля результатов, но все маршруты данных
теперь требуют авторизации и фильтруют владельца. Новые CSV, ручные отзывы
и импорт Wildberries создают связанные товар, партию и отзывы транзакционно;
повторные внешние ID сохраняют первоначальное происхождение.
До переключения анализа и запросов результатов нельзя удалять старые поля либо считать этап
обязательных связей завершённым. После назначения всех старых данных и
переключения записи потребуется отдельная миграция NOT NULL.

## Проверки и применение

```powershell
npm run db:generate
node scripts/verify-domain-migration.mjs
# Дополнительно: прочитать dump текущей БД из контейнера и проверить копию
node scripts/verify-domain-migration.mjs --source-container hia-postgres
# Сохранить custom dump локальной Docker-БД в игнорируемый каталог .cache/backups
node scripts/backup-local-db.mjs
# Проверить восстановление конкретного сохранённого dump и миграцию копии
node scripts/verify-domain-migration.mjs --backup-file PATH_TO_DUMP
```

Проверка создаёт отдельный временный PostgreSQL 16 с произвольным портом
на loopback и удаляет только собственный контейнер после отключения клиентов.
Проверяются чистая установка, dump/restore старой схемы с тестовыми записями,
миграция восстановленной копии, явное назначение владельца, ограничения,
неизменность входов и сохранность доказательств после удаления исходного
отзыва. При `--source-container` исходная БД только читается через `pg_dump`;
миграции применяются к копии. Требуются Docker и локальный образ postgres:16-alpine.

Результат этой сессии: все проверки прошли. В текущей БД было 0 отзывов;
сохранность текстов и прежних результатов проверена на синтетической старой
базе, а не на реальном массиве данных. Также прошли 40 API + 3 web теста,
TypeScript, ESLint и production-сборки.

Перед применением на БД с ценными данными сохранить отдельный dump БД и
каталог файлов отчётов и проверить восстановление. Затем выполнить
`npm run db:deploy` и `npm run db:generate`. Откат к прежней версии схемы —
восстановление проверенной резервной копии, а не удаление новых таблиц вручную.
