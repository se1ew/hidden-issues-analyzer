# Улучшение извлечения жалоб: Qwen3 4B

Сравниваются прежний метод `review-evidence-v3 / extraction-v4` и новый
`review-evidence-v5 / extraction-v9` на том же GGUF и CPU из
[первичной проверки](qwen3-4b-2026-11-15.md). Режим `json_object`, температура 0,1,
контекст 4096, выход 1024, запросы последовательно; транспортные повторы отключены.
У нового метода допускается один исправляющий запрос на фрагмент. Кэш отключён,
облако не вызывается, пользовательские отзывы и настройки аккаунтов не меняются.

## Изменения

Жалобы вложены в аспекты в ответе модели, индексы назначает сервер.
Область жалобы тоже назначает сервер: доставка/продавец/упаковка получают
соответствующие scope, остальные аспекты — product. Модель выбирает категорию.
Для стабильности запроса wire-формат v7 сохранён, включая дублирующий scope;
итоговое значение сервер выводит из категории после декодирования.
Имена аспектов ограничены словарём; промпт различает конкретный дефект,
общую оценку, отрицание, предположение и чужой опыт. Последствия должны
быть исходным фрагментом внутри цитаты. Модель выбирает `evidenceId` и
`consequenceId` из списка; сервер берёт текст и UTF-16-координаты из исходника.
Список содержит общий контекст, предложения и части предложений, максимум 64
варианта на фрагмент разбора. Ошибка схемы или доказательства вызывает одну
попытку вернуть полный JSON по исходному отзыву. Повтор проходит те же проверки.
Сервер не заменяет цитату похожей фразой и не публикует невалидный результат.
Смысл выбора ID остаётся ответственностью модели. Цитаты иногда длиннее
минимальной проблемной фразы; разделение на предложения/части эвристическое.
Общий контекст доступен даже при достижении лимита вариантов.

Узкий список общих оценок дополнительно отсекает известные фразы без дефекта.
Это не универсальный смысловой классификатор. Старые снимки, результаты,
кэш и незавершённые запуски сохраняют прежний контракт.

## Сравнение

Успешный ответ означает прохождение схемы и проверки цитат, а не автоматически
правильный смысл. TP — эквивалентный ожидаемому дефект с правильным scope;
FP — лишняя жалоба, FN — пропущенный дефект, включая отклонённый ответ.
Смысловые соответствия ниже сверены ассистентом, не независимым человеком.

### Исходные 25 примеров (20 ожидаемых жалоб)

| Показатель | Прежний v4 | Итоговый v9 |
| --- | --- | --- |
| Принятые ответы | 21/25 | 25/25 |
| TP / FP / FN | 17 / 1 / 3 | 20 / 0 / 0 |
| Совпали дефект, scope и категория эталона | 2/20 | 19/20 |
| Тональность в допустимом наборе среди принятых ответов | 19/21 | 24/25 |
| Исправляющие запросы | 0 | 1 |
| Наблюдаемое время | 198,298 с | 173,611 с |

В v9 единственный повтор — `r25`, после него корректный пустой список жалоб.
Общая оценка `r18` больше не публикуется как дефект. `r08` сохраняет правильную
связь обеих жалоб с аспектами. Все 20 цитат совпадают с исходными диапазонами.

Остались несовпадения: `r13` — functionality вместо quality в эталоне;
`r23` — negative вместо допустимых positive/neutral. В `r09` явно названное
последствие «мешает разговаривать» сохранено в цитате, но поле consequences
остаётся null. Исправленное копирование цитат не решает эти смысловые задачи.

| --- | --- | --- |
| Принятые ответы | 10/12 | 11/12 |

Прежний метод публиковал две ложные проблемы в отрицании `h02`, чужой опыт
`h04` и отклонял цитаты `h08`, `h10`. Новый принимает оба последних случая
и не публикует чужой опыт. Но ограничения остались:

- `h02`: `invalid_response` после двух попыток. Правильный пустой результат
  не получен; отсутствие опубликованной ошибки здесь не равно успешной обработке.
- `h05`: намерение «Больше ничего здесь не закажу» ошибочно опубликовано
  как жалоба на цену. Узкий фильтр известных общих оценок не универсален.
- `h12`: неверный цвет найден, но выбран аспект «упаковка» вместо «продавец»;
  сервер согласованно назначил неверный packaging scope. По строгому правилу
  совпадения scope это один FP и один FN, хотя само событие распознано.
- `h01`: functionality вместо quality в эталоне. В `h10` последствие для глаз
  не извлечено. Совпадение дефекта, scope и категории — 6/8 в новом прогоне.

Настройки и промпт v9 после результатов этого набора не менялись.
SHA-256 набора у обоих методов совпадает:
`1bb9e08f6261ce2ce1c4fd6e1c1ae169945f9c1a9a57e539a8ea4bea0a9da78e`.

Время — один наблюдаемый прогон каждого варианта. Кэш префикса runtime,
первое заполнение контекста и фоновая нагрузка отличались; это не изолированный
тест производительности и не гарантия ускорения.

## Отклонённый промежуточный вариант

Первый вариант v6 с перепечатыванием цитат принял только 17/25 результатов
и опубликовал 11 жалоб за 442,279 с. Все восемь отклонений остались после
одного повтора: семь `invalid_evidence` и один `invalid_response`.
Общая ложная жалоба исчезла, но полнота ухудшилась. Этот вариант не развёрнут.
Результат сохраняется, чтобы не скрывать неудачный эксперимент.

После перехода к ID отдельно проверены шесть известных сбоев (`r06`, `r08`,
`r10`, `r12`, `r20`, `r25`): 6/6 ответов, семь ожидаемых жалоб, один повтор.
Это отобранная диагностическая подвыборка, не самостоятельная оценка точности.

Полный промежуточный прогон v7 дал 24/25 ответов и 20 цитат за 191,712 с.
Все ожидаемые дефекты обнаружены, но упаковка в `r06` получила scope product
вместо packaging; `r18` отклонён как общая оценка. Последствия ещё не выделены.
В эксперименте v8 scope убран из wire-формата, добавлен пример последствия.
Итог — 24/25 ответа за 205,711 с, 19 правильных жалоб со scope, две лишние
жалобы (`r05`: отрицание, `r15`: положительная фраза), один пропуск (`r24`).
Последствия также ошибочны: дефект назван последствием в `r08`, а в `r09`
явное последствие по-прежнему не выделено. Этот вариант тоже не развёрнут.

В v9 возвращены точный промпт и scoped wire-формат v7. Нормализация scope
и отбрасывание известных общих оценок выполняются сервером после декодирования,
не меняя задачу модели. Принятие v9 не означает, что проблема последствий решена.

## Границы проверки

Исходные 25 примеров были известны при настройке промпта. Дополнительные
12 примеров написаны ассистентом и зафиксированы до проверки новых ответов;
на них сравниваются оба метода без последующей подгонки. Это синтетическая
проверка переноса, не независимая человеческая выборка. Контрольные суммы
дополнительного набора записаны в JSON.

Смысловую сверку проводит ассистент. Поля human adjudication, precision,
recall и утверждённые пороги в сырых отчётах остаются незаполненными.
Для вывода о точности на реальных товарах нужен отдельный набор отзывов
с независимой разметкой и проверкой пропусков, лишних жалоб и аспектов.

## Воспроизведение

После сборки API и настройки локального провайдера:

```sh
node scripts/evaluate-model.mjs --output .cache/current-original.json
node scripts/evaluate-model.mjs --baseline --dataset docs/fixtures/accuracy-transfer-cases.json --output .cache/baseline-transfer.json
node scripts/evaluate-model.mjs --dataset docs/fixtures/accuracy-transfer-cases.json --output .cache/current-transfer.json
```

Для сравнения установить `LLM_RETRIES=0`. Скрипт отказывается от облачного
провайдера и перезаписи существующего отчёта. Наличие ошибок отражается
ненулевым кодом выхода; JSON при этом сохраняется полностью.
