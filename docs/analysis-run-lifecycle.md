# Статусы и переходы запуска анализа

Правила первой версии, 11 октября 2026. Уточнение
[спецификации](product-spec.md) для будущей реализации `AnalysisRun`.
Статус запуска хранится в БД; Socket.IO передаёт его изменения, но не является
источником состояния. Закрытие страницы не отменяет запуск.

## Состояния

| Статус | Значение |
| --- | --- |
| `queued` | Состав отзывов и конфигурация сохранены, запуск ждёт worker |
| `running` | Worker владеет запуском и выполняет этапы |
| `completed` | Все отзывы и обязательные этапы успешно обработаны |
| `partial` | Есть сохранённые результаты отзывов, но обработка или обязательные этапы завершились с ошибками |
| `failed` | Обработка закончилась ошибкой, пригодных результатов отзывов нет |
| `cancelled` | Отмена владельца зафиксирована; worker остановлен, новые записи запрещены |
| `interrupted` | Выполнение потеряло worker; его право записи отозвано |

`queued` и `running` — активные состояния; остальные — терминальные.
Успешный результат отзыва с пустым списком жалоб считается пригодным.
У `partial` результаты извлечения могут быть доступны без групп проблем:
ошибка группировки явно показана, старые группы не подставляются.
AI-вывод и экспорт — отдельные операции; их ошибки не меняют статус анализа.
Обязательные этапы анализа: извлечение, группировка и сохранение итогов.
Этап хранится отдельно от статуса и указывает место ошибки или остановки.

## Разрешённые переходы

| Из | В | Условие |
| --- | --- | --- |
| `queued` | `running` | Worker атомарно получил право обработки; заполнен `startedAt` |
| `queued` | `cancelled` | Отмена раньше захвата worker; задача исключена из обработки |
| `queued` | `failed` | Неустранимая ошибка подготовки/передачи задачи; автоматические повторы исчерпаны |
| `running` | `completed` | `succeeded = total`, `failed = 0`, все обязательные этапы сохранены |
| `running` | `partial` | Есть хотя бы один успешный результат и ошибка отзыва/этапа или необработанный остаток после ошибки |
| `running` | `failed` | Ошибка без единого успешного результата |
| `running` | `cancelled` | Worker подтвердил остановку либо право записи отозвано после запроса отмены |
| `running` | `interrupted` | Потеря worker подтверждена истечением lease; его право записи отозвано |

Все остальные переходы запрещены. Терминальный статус и счётчики неизменяемы;
повторная доставка задачи или поздний ответ модели не открывают запуск снова.
Повторный анализ создаёт новый `runId`, со ссылкой на предыдущий при наличии.
Повторяемые ошибки отдельных запросов обрабатываются в `running`; ошибка
отзыва становится окончательной только после исчерпания настроенных повторов.

Пустая выборка проходит `queued → running → completed`, с нулевыми счётчиками
и причиной `empty_selection`. Невалидный запрос и отказ в доступе не создают
запуск. Отказ из-за уже активного запуска также не создаёт второй запуск.
Окончание этапов без ошибок при необработанных отзывах не даёт `completed`.

## Счётчики и результаты

`total` фиксируется по снимку отзывов до постановки в очередь.
`succeeded` и `failed` считают уникальные отзывы с сохранённым успешным
результатом или окончательной ошибкой. Повторы запроса не увеличивают их.
`processed = succeeded + failed`; `remaining = total − processed`.
Всегда `0 ≤ processed ≤ total`. Отзывы в работе входят в `remaining`.

Сохранение результата и изменение счётчиков выполняются атомарно.
Один отзыв запуска имеет один конечный результат. Прогресс отзывов 100%
не означает завершение группировки: статус остаётся `running` до сохранения
всех обязательных итогов. При `cancelled` и `interrupted` сохраняются уже
записанные результаты и может оставаться ненулевой `remaining`.

Для терминальных состояний сохраняются `finishedAt`, причина завершения
и диагностика ошибок без секретов. `startedAt` может отсутствовать у запуска,
отменённого или провалившегося в очереди. История переходов содержит время,
исходное/новое состояние и инициатора (владелец, worker или восстановление).

## Отмена, восстановление и гонки

Запрос отмены устанавливает `cancelRequestedAt`. Пока выполняется текущая
работа, запуск остаётся `running`, а UI показывает «Останавливается».
После фиксации запроса нельзя брать следующий отзыв или новый этап.
Текущий запрос прерывается по возможности; его поздний ответ не сохраняется.
При завершении уже начатой транзакции до фиксации запроса её результат остаётся.
Сам факт отправки `AbortSignal` не подтверждает остановку worker.

Проверка права worker, отсутствие запроса отмены, запись результатов и смена
статуса защищены одной атомарной операцией с версией состояния/токеном lease.
Если отмена зафиксирована первой, worker не может завершить запуск как
`completed`, `partial` или `failed`. Если терминальное состояние зафиксировано
первым, отмена возвращает текущий статус без изменений. Повторная отмена
идемпотентна и не создаёт новых переходов.

Worker поддерживает lease с heartbeat; интервал и срок lease задаются
конфигурацией, а не выводятся из времени последнего socket-события.
При потере lease восстановление атомарно отзывает право записи и фиксирует
`interrupted`; при ранее сохранённом запросе отмены — `cancelled`.
Живой worker другого процесса нельзя считать погибшим из-за рестарта API.
Разрыв socket-соединения не меняет статус. Сохранённый `queued` после рестарта
остаётся в очереди и восстанавливает доставку идемпотентно; если доставка
окончательно невозможна, применяется переход `queued → failed`.

Один активный запуск на товар обеспечивается атомарно. Ограничение снимается
только после терминального перехода и отзыва права записи старого worker.
Удаление товара возможно после этого, с проверкой владельца. Терминальные
результаты доступны по `runId` после перезагрузки страницы и рестарта API.

## Сценарии будущей приёмки

| Условия | Ожидание |
| --- | --- |
| 3 отзыва, все успешны, группировка сохранена | `completed`, total=3, succeeded=3, failed=0, remaining=0 |
| 3 отзыва, 2 успешны, 1 ошибка; группировка успешных завершена | `partial`, total=3, succeeded=2, failed=1, remaining=0 |
| Все 3 отзыва завершились ошибкой | `failed`, total=3, succeeded=0, failed=3, remaining=0 |
| 3 успешных отзыва, ошибка группировки | `partial`, succeeded=3, failed=0; ошибка этапа видна, группы недоступны |
| Общая ошибка после 1 успеха, 2 отзыва не начаты | `partial`, total=3, succeeded=1, failed=0, remaining=2 |
| Успешный анализ без жалоб | `completed`, пустые группы, нет вымышленных дефектов |
| Нет выбранных отзывов | `completed`, все счётчики 0, причина `empty_selection` |
| Отмена в очереди | `cancelled`, startedAt отсутствует, worker не начинает обработку |
| Отмена после 1 успеха из 3 | `cancelled`, succeeded=1, remaining=2; поздний ответ не записывается |
| Потеря lease после 1 успеха из 3 | `interrupted`, succeeded=1, remaining=2; старый worker больше не пишет |
| Потеря lease после принятой отмены | `cancelled`, результаты сохранены |
| Завершение и отмена одновременно | Побеждает первая атомарная запись; статус не перезаписывается |
| Двойная доставка задачи / повтор результата | Один worker, один результат отзыва, счётчики не удваиваются |
| Рестарт API при живом worker / разрыв socket | Статус не меняется; клиент получает состояние из БД |

Эти сценарии ещё не реализованы и не проверены на production-пайплайне.
Текущий контроллер использует `analyzing/complete/error` в памяти,
игнорирует число ошибок отзывов при завершении и отмечает отмену как `error`.
Это не удовлетворяет описанному контракту; реализация относится к фазам
модели данных, очереди и API.
