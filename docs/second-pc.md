# Осталось на втором ПК

Разработка и программная приёмка на основном ПК выполнены. Все открытые
пункты перечислены в `TASKS.md`; здесь порядок их выполнения на сервере с
GTX 1080. Программная проверка управляемой моделью не заменяет реальные
измерения. Wildberries дополнительно зависит от доступности внешнего сервиса.

## Что переносить

Комплект: `.cache/offline-bundle` на основном ПК. Он содержит `images.tar`
(приложение + PostgreSQL + Redis), `repository.bundle` с историей Git,
`source.zip`, готовые эмбеддинги, `manifest.json` и `verify.ps1`.
Пробный комплект прошёл проверку всех SHA-256; финальный commit указан в manifest.
Пользовательские `.env`, БД и отчёты в комплект не включены. Их резервные копии
переносятся отдельно при необходимости. Runtime и instruct GGUF ещё не выбраны.

1. Установите Docker Desktop с Linux containers и Git. Для host-команд
   обслуживания нужен Node 24; production из готового образа npm не требует.
2. Скопируйте весь комплект и проверьте его в Windows PowerShell:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File D:\Transfer\offline-bundle\verify.ps1
   docker load --input D:\Transfer\offline-bundle\images.tar
   git clone D:\Transfer\offline-bundle\repository.bundle D:\ReviewLens
   git -C D:\ReviewLens remote set-url origin https://github.com/se1ew/hidden-issues-analyzer.git
   ```

   Сверьте `git rev-parse HEAD` с `sourceCommit` manifest. `source.zip` —
   альтернатива для запуска без Git; для дальнейших коммитов используйте bundle.
3. Из `D:\ReviewLens` выполните Init; установите параметры runtime после его
   проверки. Секреты создаются заново и не копируются из примеров как заглушки.

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/app.ps1 -Action Init
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/app.ps1 -Action Start
   ```

   Build не нужен при загруженных образах. Перенесите embeddings в volume по
   [командам deployment.md](deployment.md#комплект-переноса-без-скачивания-npm-пакетов)
   и выполните offline-проверку внутри worker. Сохраните `EMBEDDING_LOCAL_ONLY=true`.

## GPU, runtime и настоящая модель

1. Снимите отчёт именно этого ПК:
   `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check-gpu.ps1`.
   Проверьте GTX 1080, драйвер, общую и свободную VRAM. После установки runtime
   повторите с `-RuntimePath PATH_TO_LLAMA_SERVER`; нужен лог фактического offload.
2. По [local-model.md](local-model.md) проверьте совместимый runtime и небольшую
   квантованную instruct-модель с одним запросом. Пока это испытание, рабочая
   версия/модель не объявлены выбранными. Скачайте точные артефакты, запишите
   revision/SHA-256 и пути вне контейнера. Не путайте порт модели 8081 с 8080 приложения.
3. Проверьте `/v1/models` и реальное извлечение через локальный адаптер из
   контейнера. На основном ПК подтверждён доступ контейнера к Windows loopback
   через `host.docker.internal`; на целевом ПК это нужно повторить с runtime.
4. Согласуйте критерии и выполните [протокол качества](model-evaluation.md).
   Сохраните ответы/ошибки, точность/полноту после ручной разметки, холодную
   загрузку runtime, первый/прогретый запрос, пачку и пик VRAM/RAM во время работы.
   При недостаточном результате испытайте меньшую модель/другой runtime.
5. Запишите итоговые имя GGUF/runtime/драйвера, квантование, context, offload,
   parallel, лимиты/таймауты, скорость и ограничения в `local-model.md` и
   `acceptance.md`. Заглушки `LLM_MODEL`/`LLM_MODEL_VERSION` замените фактическими.
6. Отключите интернет и повторите импорт, анализ, цитаты, группировку и отчёт.
   Не должно быть обращения к OpenRouter или скачивания файлов. Проверьте
   готовый и новый запуск, а также навигацию после остановки модели.

## LAN, автозапуск и восстановление

1. Выберите реальную сеть демонстрации и IPv4 сервера. Настройте `APP_BIND`,
   `WEB_ORIGIN` и Firewall по deployment.md, затем откройте приложение с основного
   ПК. Проверьте вход, cookie, Socket.IO и скачивание. PostgreSQL/Redis/runtime
   должны оставаться недоступными браузеру/постороннему устройству.
2. Если LAN недоступна, выполните `app.ps1 -Action Local` и используйте браузер
   сервера. Физический проектор проверьте отдельно, если он входит в показ.
3. Подготовьте скрипт фонового запуска выбранного runtime и установите автозапуск
   `app.ps1 -Action InstallAutostart -RuntimeScript ABSOLUTE_PATH`.
   Перезагрузите Windows, войдите в аккаунт и проверьте runtime, Docker Desktop,
   Status/readiness, данные, новый анализ и скачивание сохранённого отчёта.
4. Сделайте production backup и восстановите его в отдельный пустой project;
   команды и запрет перезаписи — в deployment.md. После перезагрузки проверьте
   именно восстановленную установку. Исходную установку сохраняйте до приёмки.
5. Из сети демонстрации повторите живую проверку WB с реальным артикулом:
   `node scripts/verify-wildberries-live.mjs --product NM_ID`. При недоступности
   источник остаётся непроверенным; используйте демо-CSV и зафиксируйте отказ.

## Итоговый показ и коммиты

Пройдите [demo-walkthrough.md](demo-walkthrough.md) с 17 отзывами чайника A,
покажите две исходные цитаты и совпадение отчёта с сохранённым запуском.
Проверьте установку по README именно здесь, измеренные ограничения и отсутствие
блокирующих ошибок. После целевой приёмки выполните согласованные проверки
и создайте финальный release-тег.

Каждый отдельный пункт закрывайте собственным коммитом и сразу push.
Заголовок — кратко о фактическом изменении, без номеров фаз/задач. Результаты
проверки без интернета коммитьте и пушьте после восстановления соединения.
Аппаратные пункты отмечайте выполненными только по результатам этого ПК.
